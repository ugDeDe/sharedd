# Техническое задание: доработка ЛК и автоматизации sharedd

**Статус:** план для передачи исполнителю, не реализовано.
**Дата:** 2026-10-19.
**Назначение:** самостоятельное подробное ТЗ для DeepSeek или другого исполнителя.

План охватывает доработку ЛК, автоматизации, быстрых параметров ноды и публичных названий. Названия новых таблиц, полей и маршрутов ниже — предлагаемый контракт реализации, а не описание уже существующих функций. Существующие механизмы нужно переиспользовать, не создавая параллельную систему.

## 0. Как выполнять задание

### Цель

Пользователь должен иметь возможность:

1. Создать ноду без редактирования shell-команд профиля.
2. При создании быстро указать имя ноды, ad_tag и остальные поддерживаемые параметры.
3. Изменить название и поддерживаемые настройки существующей ноды из её карточки.
4. Видеть, какие настройки сохранены и какие действительно применены.
5. Получать автоматическую замену с сохранением индивидуальных параметров.
6. Понимать состояние установки, восстановления и оплаты.
7. Не создавать повторные платные заказы из-за потери ответа.
8. Видеть в публичной статистике для пользовательской ноды логин аккаунта и постоянный номер ноды, а для ноды без пользовательского владельца — прежнее имя из регистрации.

### Порядок выполнения

**Не реализовывать всё одним большим изменением.** Работать последовательно по этапам из раздела 19.

Для каждого этапа:

1. Прочитать соответствующий код.
2. Описать, какие существующие функции будут переиспользованы.
3. Написать тесты.
4. Реализовать изменение.
5. Выполнить проверки.
6. Отчитаться по критериям приёмки.
7. Только после этого переходить дальше.

### Запреты

Без отдельного разрешения владельца проекта запрещено:

- выполнять реальные покупки VPS;
- удалять реальные VPS;
- менять IP реальных серверов;
- запускать установщики на рабочих нодах;
- изменять production-БД;
- деплоить изменения;
- отправлять реальные пароли, ключи и токены внешним сервисам;
- менять бизнес-правила квот;
- отключать существующие политики автоматизации при миграции;
- переписывать проект на другой frontend-фреймворк;
- заменять SQLite на другую БД;
- внедрять брокер сообщений или отдельный workflow-сервис.

Все автоматические проверки внешних действий выполнять через локальные фейки и httptest.

## 1. Зафиксированные требования пользователя

Эти требования не обсуждать заново и не заменять собственными предпочтениями.

### 1.1. Параметры ноды

При создании ноды должны быть доступны обычные поля формы:

- имя ноды;
- ad_tag;
- параметры выбранного профиля, разрешённые для установки.

Ради изменения этих значений пользователь не должен открывать и править текст профиля. Изменение параметров одной ноды не изменяет сам профиль и остальные ноды.

### 1.2. Публичное название пользовательской ноды

Если существует подтверждённая привязка ноды к обычному пользовательскому аккаунту, отображать:

```text
login · Нода №2
```

Используется реальный логин аккаунта. Не вводить вместо этого отдельное публичное имя, никнейм для статистики, переключатель анонимности или обязательное согласие на показ логина. Пользователь проекта прямо выбрал отображение логина.

Публичность логина не означает разрешения публиковать email, внутренний ID аккаунта, токены и другие данные.

### 1.3. Нода по общему токену без пользовательского владельца

Показывать так же, как до изменений: имя/идентификатор из регистрации, который сейчас используется интерфейсом. Например:

```text
helsinki-abc12
```

Не заменять его на «Нода проекта №1», «Анонимная нода», «Участник пула» или «legacy · Нода №1». Никакого предполагаемого владельца такой ноде не назначать.

### 1.4. Источник владения

Владение определяется по сохранённой серверной привязке аккаунта. Запрещено определять владельца по IP, имени ноды, префиксу технического ID, ad_tag, MTProto-секрету или последнему аккаунту, открывавшему карточку.

Общий токен регистрации агента и MTProto-секрет прокси — разные сущности. Если нода использует общий MTProto-секрет, но имеет подтверждённого пользовательского владельца, она всё равно отображается с логином владельца.

## 3. Неизменяемые технические инварианты

### 3.1. Технический ID ноды

node_id — постоянный технический идентификатор формата NAME-HASH. Имя соответствует существующим ограничениям, суффикс генерируется существующим механизмом.

Обычное переименование в ЛК не должно менять /var/lib/sharedd/node_id, секрет ноды, владельца, историю или квоту; не должно запускать переустановку или создавать VPS.

### 3.2. Системные переменные

Пользователь не может передать через vars:

```text
node_id
node_secret
registry_url
label
```

Имя ноды передаётся отдельным полем API. Сервер проверяет его и сам подставляет label. Нельзя ради удобства формы убрать защиту label из validateEditableVarName.

### 3.3. Общий порт

shared_proxy.port остаётся источником истины для допуска ноды в общий пул. Редактирование установки не меняет правила допуска.

Если пользователь выбирает другой порт, показывать существующее предупреждение, не обещать участие в общем пуле и не изменять конфигурацию регистратора автоматически.

### 3.4. Внешние действия

- Не повторять платный Create при неопределённом исходе.
- Отсутствие локального воркера не доказывает отсутствие оплаченного VPS.
- Успешный ответ Delete не доказывает завершённое удаление.
- Ошибка установки не должна покупать новый VPS.
- Повтор установки работает с уже созданным сервером.
- Нельзя автоматически откатывать финансовую операцию удалением VPS без явно определённых правил и разрешения.

## 4. Разделить три понятия ноды

### 4.1. Техническая нода

Конкретный агент, например node_id=frankfurt-a1b2c. Имеет секрет, IP, метрики, историю регистрации и состояние здоровья.

### 4.2. Логическая нода пользователя

Постоянное место в списке: login · Нода №2. Переживает рестарт агента, временное исчезновение из пула, повторную регистрацию, переустановку, автоматическую замену VPS, изменение IP и смену node_id в подтверждённом процессе замены.

### 4.3. Облачный ресурс

Конкретный оплачиваемый VPS у провайдера. При замене логическая нода №2 переходит со старого VPS на новую техническую ноду на новом VPS. Номер остаётся прежним.

Не использовать ID VPS или позицию строки в таблице как номер ноды пользователя.

## 5. Хранение логической ноды и постоянного номера

### 5.1. Новая таблица node_slots

Предлагаемые поля:

```text
id                  INTEGER PRIMARY KEY
user_id             INTEGER NOT NULL
number              INTEGER NOT NULL
name                TEXT NOT NULL
revision            INTEGER NOT NULL DEFAULT 1
created_at          INTEGER NOT NULL
updated_at          INTEGER NOT NULL
archived_at         INTEGER NULL
```

Ограничения:

```text
FOREIGN KEY(user_id) REFERENCES users(id)
UNIQUE(user_id, number)
CHECK(number > 0)
```

id — внутренний постоянный ID логической ноды; number — публичный номер внутри аккаунта; name — редактируемое название в ЛК и имя будущих установок; revision — optimistic locking.

В первой реализации name совместим с коротким именем установщика: существующие ограничения 1–10 символов. Не вводить одновременно дополнительные alias/display_name/hostname без отдельного сценария.

### 5.2. Связь с владельцем

Добавить nullable-связь slot_id к node_owners либо отдельную таблицу привязок с теми же гарантиями. Предпочтительный вариант — node_owners.slot_id.

Проверки:

- слот принадлежит тому же user_id, что и node_owners;
- legacy-строки не получают пользовательский слот;
- связь устанавливается сервером;
- клиент не может указать чужой слот;
- исторические технические ноды могут ссылаться на один логический слот.

Не вводить UNIQUE(slot_id) в node_owners: при замене могут существовать старый и новый технические ID.

### 5.3. Выделение номера

Выделять транзакционно. Использовать постоянный счётчик пользователя либо эквивалентный механизм, исключающий повторное использование номера.

Правила:

1. Номера положительные и уникальные внутри аккаунта.
2. После удаления старый номер не выдаётся другой ноде.
3. Пропуски допустимы.
4. Две конкурентные операции не получают одинаковый номер.
5. Повтор одной идемпотентной команды не создаёт второй слот.

Вариант таблицы:

```text
user_node_counters:
    user_id PRIMARY KEY
    next_number NOT NULL
```

Выделение номера и создание слота — в одной транзакции.

### 5.4. Когда создавать слот

- Через ЛК: при принятии команды создания/установки.
- Регистрация через authkey вне ЛК: при первой успешной привязке владельца.
- Повторная регистрация: имеющийся слот.
- Переустановка: слот исходной установки.
- Автозамена: слот заменяемой ноды.
- Общая legacy-регистрация: слот не создаётся.

Создание слота не занимает квоту пула. Слот — не новая система квот.

### 5.5. Миграция старых данных

Для существующих неlegacy владельцев сортировать по registered_at, затем node_id; назначить номера детерминированно внутри пользователя; сохранить в БД; повторный запуск не перенумеровывает записи.

Не объединять исторические ноды по совпадению IP или имени. Если историческую замену нельзя доказать существующими связями, не угадывать её.

Миграция транзакционная, повторяемая, не меняет quota_reservations и токены, не вызывает сеть и не удаляет существующие записи.

## 6. Правила публичного отображения

### 6.1. Вычислять подпись на сервере

Добавить поля публичных DTO:

```json
{
  "node_id": "frankfurt-a1b2c",
  "display_name": "demo_user · Нода №2",
  "owner_username": "demo_user",
  "owner_node_number": 2
}
```

Для legacy:

```json
{
  "node_id": "helsinki-abc12",
  "display_name": "helsinki-abc12"
}
```

owner_username и owner_node_number отсутствуют. node_id не переименовывать и не менять смысл: он продолжает использоваться в URL, data-id, запросах API, событиях и выборе ноды.

### 6.2. Алгоритм

```text
Подтверждённый обычный владелец и слот:
    display_name = username + " · Нода №" + number

Владелец legacy или отсутствует:
    display_name = прежнее отображаемое значение регистрации
```

При временной недоступности пользовательской БД не придумывать логин или владельца, не менять нумерацию. Допустим временный fallback на node_id. Сбой разрешения подписи не ломает весь публичный список.

### 6.3. Где обновить отображение

Проверить список /statistics, страницу ноды, блок мастеров доменов, публичные списки карантина и другие элементы публичной статистики с названием текущей ноды.

Общий frontend-helper:

```text
nodeDisplayName(node) = node.display_name || node.node_id
```

Одно правило, без копирования. Не менять формат исторических событий массовой перезаписью.

### 6.4. Производительность и безопасность

- Не выполнять SQL-запрос отдельно на каждую ноду: метаданные получать пакетно.
- Не выполнять SQL под длительно удерживаемым r.mu.
- Не сериализовать User целиком.
- Сохранить маскирование IP.
- Не публиковать секреты и measurement ID.
- Экранировать логин и имя при HTML-рендеринге.

### Приёмка

- Две ноды пользователя имеют разные постоянные номера.
- Сортировка списка и рестарт номера не меняют.
- Замена VPS сохраняет номер.
- Legacy выглядит как раньше.
- Старый frontend с node_id продолжает работать.
- Публичные ответы не содержат лишних приватных полей.

## 7. Быстрые параметры установки

### 7.1. Не создавать новый формат вместо vars_schema

Расширить существующий ProfileVar необязательными полями:

```json
{
  "vars": [
    {
      "name": "ad_tag",
      "label": "Рекламный тег",
      "description": "Используется для этой ноды",
      "type": "string",
      "default": "",
      "required": false,
      "secret": false,
      "group": "basic",
      "update_mode": "runtime"
    }
  ]
}
```

Допустимые type: string, integer, boolean, enum. group: basic, advanced. update_mode: install_only, runtime. Для enum — options, для строки — max_length.

Старые схемы без полей работают как раньше. Отсутствующий update_mode — install_only.

Декларация runtime в произвольном профиле не разрешает выполнение команды на агенте: параметр входит в серверный allowlist и поддерживается агентом.

Имя ноды — отдельное поле команды, не vars_schema.

### 7.2. Приоритет значений

```text
Явные значения формы
    > Личные значения для выбранного профиля
    > Непустые значения профиля
    > Существующие значения регистратора для поддерживаемых стандартных ключей
```

Для ad_tag не придумывать значение регистратора, если такого контракта нет.

### 7.3. Пустая строка и наследование

```text
Ключ не передан → наследовать
Ключ передан как "" → явно пустое значение
ad_tag отсутствует → наследовать
ad_tag = "" → установить без рекламного тега
proxy_port = "" → ошибка
```

Не определять наличие override через truthiness. Проверять наличие ключа.

### 7.4. Alias

Сохранить port→proxy_port, sni→proxy_sni, secret→proxy_secret. Конфликтующие значения alias и канонического имени отклонять. ad_tag_* не превращать автоматически в alias ad_tag.

### 7.5. Валидация ad_tag

Для стандартного тега MTProto: пустая строка допустима; непустое значение — 32 hex-символа; нормализация lowercase; обрезка пробелов по краям; отказ до установки при неправильном формате. Для других имён параметров эту проверку автоматически не применять.

### 7.6. Личные defaults

Хранить для конкретного профиля:

```text
user_profile_defaults:
    user_id
    profile_id
    vars_json
    secret_vars_enc
    revision
    updated_at
PRIMARY KEY(user_id, profile_id)
```

Не хранить имя текущей ноды, node_id, node_secret, registry_url, SSH-пароль сервера. Обычные параметры и секреты хранить отдельно.

В UI выключенный по умолчанию checkbox «Использовать эти параметры по умолчанию для этого профиля». Сохранение defaults — отдельное действие. Не менять их незаметно после каждой установки.

## 8. Единая форма параметров во всех сценариях

### 8.1. Общий компонент

Переиспользовать ui/lib/vars.ts. Режим установки:

```text
Название ноды
Профиль установки
Основные параметры:
    Рекламный тег
    Другие basic-параметры
Расширенные параметры:
    Порт
    SNI
    Секрет — в рамках разрешённого контракта
    Остальные advanced-параметры
```

Пользователь редактирует значения, не имена стандартных переменных. Показывать источник: «Из профиля», «Из личных настроек», «Из регистратора», «Для этой ноды».

«Сбросить переопределение» удаляет override, а не отправляет пустую строку вместо наследования.

### 8.2. Сценарии

Обязательно подключить к установке и переустановке собственного VPS, созданию cloud-ресурса с установкой, установке на существующий cloud-ресурс, автопилоту, старому Beget-сценарию и первичной установке graph-процесса, если путь доступен.

Не считать задачу завершённой, если работает только один визард.

### 8.3. Автопилот

Расширить fleetCreateBody:

```json
{
  "name": "fra",
  "count": 2,
  "installation_profile_id": 6,
  "installation_vars": {
    "ad_tag": "0123456789abcdef0123456789abcdef"
  },
  "auto_replace": false
}
```

Остальные обязательные поля существующего запроса сохраняются. В первой версии одно базовое имя и один набор параметров на пакет; сформированные имена показать до подтверждения; для count>1 сохранить существующую схему суффиксов и ограничение длины имени. Не добавлять пока таблицу разных параметров каждого элемента.

Не оставлять захардкоженное name="fleet" вместо пользовательского поля. installation_vars передавать через общую процедуру установки, не новый shell-runner.

### 8.4. Смена профиля

Сохранять общие поля вроде имени; перечитывать схему; пересчитывать наследование; не переносить несовместимые поля молча; предупреждать перед удалением несохранённых специфичных значений. Ошибка загрузки схемы не равна пустой схеме.

## 9. Неизменяемый снимок установки

### 9.1. Причина

Профиль редактируется на месте. Без снимка восстановление может использовать другой текст, замена — другой ad_tag; расследование теряет точные команды, изменения общего профиля влияют на ранее настроенные процессы.

### 9.2. Состав

До запуска установки сохранить immutable-снимок:

```text
slot_id
profile_id
profile_content_hash
steps
vars_schema
resolved_nonsecret_vars
resolved_secret_vars_enc
node_name_at_acceptance
runtime_settings_at_acceptance
created_at
```

Хранить уже разрешённые значения, не только ссылки на изменяемый профиль. Системные секреты — только в разрешённом зашифрованном виде или через защищённые ссылки.

### 9.3. Повтор и переустановка

- Восстановление процесса использует тот же снимок, не свежий профиль.
- Повтор после ошибки по умолчанию использует тот же снимок.
- Явная переустановка с новыми параметрами создаёт новый снимок после подтверждения.

Существующая операция установки может переиспользоваться: нельзя хранить единственный снимок в изменяемом поле без истории. Нужна связь operation_id+attempt_no→installation_spec_id либо эквивалентная immutable-таблица попыток. Повтор того же запроса с тем же ключом новую попытку не создаёт.

### 9.4. Автозамена

Сохранить слот, индивидуальные параметры, зафиксированный профиль и имя будущей установки. Не брать свежую редакцию профиля незаметно.

Если ad_tag изменён после первой установки, замена использует актуальное сохранённое индивидуальное значение, а не старый тег первоначального снимка. Остальные install-only параметры — принятый снимок, пока пользователь явно не изменил будущие настройки.

## 10. Редактирование существующей ноды

### 10.1. Карточка

Раздел «Параметры»: название, рекламный тег. Остальные параметры показывать с режимом «Можно применить на работающей ноде», «Требуется переустановка», «Не поддерживается текущей версией агента».

Не сохранять всё в БД с ложной надписью «Применено».

### 10.2. Переименование

Изменение node_slots.name сразу меняет ЛК, не перезапускает прокси, не меняет node_id и публичную подпись login · Нода №N. Новое имя используется следующей новой технической установкой.

Текст формы: «Название в кабинете изменится сразу. Технический ID работающей ноды останется прежним».

### 10.3. Предлагаемый API

```text
GET /api/me/nodes/{node_id}/settings
PATCH /api/me/nodes/{node_id}/settings
```

```json
{
  "expected_revision": 8,
  "name": "fra-main",
  "runtime": {
    "ad_tag": "0123456789abcdef0123456789abcdef"
  }
}
```

Изменения частичные: отсутствующее поле не меняется; неизвестные поля отклоняются; пустой ad_tag явно удаляет тег; expected_revision обязателен; конфликт — 409 revision_conflict; чужая нода — 404; отключённый пользователь не меняет настройки. Mutation требует session+CSRF, runtime-команда — Idempotency-Key.

Переименование без runtime-изменений не запускает применение агентом.

## 11. Подтверждаемое применение ad_tag агентом

Это backend+agent-задача, не только frontend-форма.

### 11.1. Без произвольных команд

Передавать только поддерживаемые параметры. Не добавлять exec/run_command/shell/apply_script API ради изменения тега.

### 11.2. Состояния

Хранить desired_revision, applied_revision, apply_state, last_error_code, last_report_at. Состояния: not_managed, pending, applying, applied, failed, unsupported.

Метаданные названия и runtime-revision различаются: переименование меняет ревизию метаданных; ad_tag — runtime-revision.

### 11.3. Неуправляемое значение не равно очистке

```text
unmanaged → не трогать существующий ad_tag
set → установить тег
clear → явно удалить тег
```

При миграции старых нод ad_tag=unmanaged. Не рассылать пустой тег с уничтожением существующих настроек.

### 11.4. Расширение /config

Совместимые необязательные поля:

```json
{
  "node_settings_protocol": 1,
  "node_settings": {
    "revision": 3,
    "ad_tag": {
      "mode": "set",
      "value": "0123456789abcdef0123456789abcdef"
    }
  }
}
```

При отсутствии управления node_settings можно не отдавать. Индивидуальные настройки разрешать только аутентифицированной ноде с подтверждённой привязкой.

Не отдавать настройки произвольного node_id только по общему токену и подставляемому заголовку. Использовать персональный секрет ноды. Legacy-клиентам сохранить прежние общие настройки.

### 11.5. Подтверждение

Новый маршрут:

```text
POST /api/node/settings/status
```

```json
{
  "node_id": "fra-main-a1b2c",
  "protocol_version": 1,
  "capabilities": ["ad_tag"],
  "attempted_revision": 3,
  "applied_revision": 3,
  "state": "applied",
  "error_code": ""
}
```

Использовать requireNodeAuth, проверку node_id/персонального секрета, строгую валидацию, лимит тела и безопасные коды ошибок.

Подтверждение хранить по технической ноде, не только по слоту: старый агент после замены не подтверждает новый VPS.

Существующий /report строго отклоняет неизвестные поля. Не расширять его без механизма совместимости. Новый агент отправляет status только если сервер объявил node_settings_protocol=1. На старом регистраторе новый агент продолжает работать без этой функции.

### 11.6. Реальное применение

Расширить существующий конвейер:

```text
валидация → подготовка → сохранение исходного состояния → применение
→ перезапуск при необходимости → ожидание готовности → readback → подтверждение
```

При ошибке восстановить предыдущее состояние.

Для MTProxyL недостаточно изменить сгенерированный config.toml: учесть источник настроек, из которого он пересоздаётся. Транзакция охватывает управляющую настройку, конфиг, перезапуск, readback и откат обоих уровней. Проверить поддерживаемый CLI используемой версии, не придумывать команды по памяти.

Для classic telemt/MEKO проверить реальный формат ad_tag. Если механизм не подтверждён, capability не объявлять, возвращать unsupported и показывать ограничение. Не писать неизвестный TOML-ключ в надежде на поддержку.

### 11.7. Повторы и рестарт-циклы

- Та же revision повторно не перезапускает прокси.
- Совпадающее значение подтверждается без рестарта.
- Ошибка не вызывает бесконечный повтор на каждом sync-тике.
- Автоповторы ограничены и только для временных ошибок.
- После исчерпания — failed.
- Явный повтор создаёт контролируемую попытку.
- Старый ack не уменьшает applied_revision и не подтверждает новую revision.
- После рестарта агент сверяет реальную настройку, а не только локальный флаг.

### Приёмка

1. Тег A не меняет B и профиль.
2. Успех только после ack агента.
3. Недоступный агент даёт pending.
4. Ошибка откатывает предыдущее рабочее состояние.
5. Повтор запроса не вызывает серию рестартов.
6. Старый агент отображается как unsupported.
7. Миграция не очищает старый тег.
8. После рестарта MTProxyL новый тег сохраняется.

## 12. Безопасность платных команд

### 12.1. Frontend-намерение

До первого POST создать объект command_kind, idempotency_key, immutable_body, body_hash, created_at, state, returned_operation_id/resource_id/fleet_id.

Состояния: draft, submitting, accepted, unknown, rejected. Сетевая ошибка после отправки — unknown, не rejected. Повтор unknown использует исходное тело и ключ. Новый ключ только для явно нового намерения.

### 12.2. Исправления

- Автопилот: убрать новый newIdemKey на каждый submit одного заказа.
- Создание ресурса: убрать автоматическую замену ключа при конфликте.
- Пакеты: отдельная сохранённая идентичность каждого элемента.
- Graph-команды: исправить недостижимый recovery после неизвестного исхода.

### 12.3. Браузерное хранение

Не хранить секреты в localStorage, URL, console или HTML data-атрибутах. Для несекретных cloud-команд допустим scoped sessionStorage, переживающий reload; проверять текущий аккаунт, очищать при logout.

Для команд с секретами использовать серверный ID принятой команды и безопасную сверку, не сохранение паролей в браузере.

### 12.4. Серверная идемпотентность

Проверять пользователя, вид команды, каноническое тело, ресурс, установочные параметры и профиль/снимок. В fleetReplayMatches учесть имя пакета и новые переменные.

Тот же ключ с другим телом — 409 idempotency_conflict, без воркера и изменения исходного заказа.

Обязательный тест: сервер принимает и сохраняет флот, обрывает ответ; повтор возвращает тот же флот; количество платных Create не растёт.

## 13. Согласие на автоматические расходы

### 13.1. Новые создания

auto_replace по умолчанию false. Отдельное согласие: «Разрешаю автоматическое создание платной замены при подтверждённой блокировке ноды». Первичная покупка и будущие покупки — разные решения.

### 13.2. Итог перед запуском

Провайдер/подключение, количество VPS, имена, профиль, ad_tag, период оплаты, оценка стоимости, правила автозамены.

При неизвестной цене: «Стоимость не удалось получить. Заказ может привести к списанию средств у провайдера». Не выдумывать цену.

### 13.3. Ограничители

Отдельным этапом после идемпотентности: лимит платных действий за 24 часа, максимум оплачиваемых ресурсов, предел цены при проверяемой оценке, cooldown, остановка покупок при неизвестных исходах.

Проверять сервером до внешнего вызова, транзакционно. Не подменять max_nodes: квота пула и финансы различаются. Числа не придумывать и не хардкодить в UI — они задаются настройками.

Миграцию правил существующих политик согласовать отдельно, не отключать их молча.

## 14. Восстановление после рестарта и честные состояния

### 14.1. Флоты

Добавить startup/periodic-подхват без повторного POST браузером.

- pending: продолжить неначатый этап;
- creating: сверить имеющийся ресурс/операцию;
- installing: восстановить по снимку;
- завершённый: не повторять;
- неизвестный платный исход: только сверка;
- ошибка: не покупать новый VPS автоматически.

Штатный shutdown не записывать как обычную пользовательскую ошибку, из-за которой recovery пропустит элемент.

### 14.2. Удаления

Восстанавливать deleting: найти операцию, read-only проверить провайдера, при отсутствии VPS завершить локально, при наличии продолжить разрешённый сценарий, при неизвестном результате сохранить состояние/причину. Внешний ID не очищать до доказанного отсутствия.

### 14.3. Готовность

Предлагаемые состояния:

```text
pending
creating
installing
verifying
admitted
error
needs_attention
```

admitted означает завершённую установку, подтверждённую регистрацию и актуальные успешные проверки. Зарегистрирован, но GP нет — verifying. Бюджет проверки истёк — needs_attention либо отдельный терминальный код, не ложный успех и не новая покупка.

### 14.4. Бюджеты времени

Сохранять начало/deadline этапа. Рестарт не обнуляет ожидание бесконечно.

## 15. Цельный пользовательский сценарий ЛК

### 15.1. Оболочка

Сохранить токены, общие компоненты, темы, модалки, защиту фокуса polling и hash-маршрутизацию, если её достаточно. Цель — связать сценарии, а не нарисовать другие карточки.

### 15.2. Первый экран

Выбор: «У меня уже есть VPS», «Купить и настроить VPS», «Настроить автоматические замены». Не раскрывать большую платную форму как единственный очевидный путь. Нулевую квоту объяснять заранее, не выдавая за финансовый лимит.

### 15.3. Карточка

Название, публичная подпись login · Нода №N, технический node_id, VPS/manual-host, установка, здоровье, применение настроек, политика, последняя операция.

Действия: «Параметры», «Проверки», «История», «Автоматизация», «Переустановить». Опасные действия — отдельная зона.

### 15.4. Ошибка и следующий шаг

Пример: «VPS создан. Установка завершилась ошибкой. Сервер продолжает оплачиваться. Повтор установки использует этот VPS и не создаёт новый».

Действия: «Повторить установку», «Открыть диагностику», «Открыть VPS», «Удалить VPS». Не использовать неоднозначное «Повторить всё».

### 15.5. Разные удаления

Различать удаление из пула, удаление/отвязку manual-host и удаление оплачиваемого VPS у провайдера. В подтверждении указывать, прекратится ли оплата. Не обещать этого после локального удаления строки.

### 15.6. Флоты/операции

- Видимый копируемый ID операции.
- resource_id — ссылка.
- История флотов, не только последний ID.
- Из ноды доступен запуск, из запуска — ресурс/нода.
- Исправлен список #/resources.
- Возврат сохраняет исходный объект.

### 15.7. Независимая загрузка

Разделить аккаунт, ноды, операции, подключения, Beget. Ошибка вторичного API не блокирует остальные. Каждый блок: loading/error/empty, время последнего успеха, retry. Ошибка не равна пустому списку.

### 15.8. Beget

Объяснить старый/новый контуры, не обещать неподдерживаемое, после подключения вести к доступному действию, 2FA-ошибку показывать у поля. Перезагрузка страницы не единственный путь выхода из локального rate-limit состояния. Не выполнять серию автоматических auth-повторов.

### 15.9. Язык

«Обновить GET» → «Проверить состояние»; Invocation → «Запуск шага»; Checkpoint → «Точка восстановления». Технические названия — раскрываемые детали.

## 16. Шаблоны автоматизации

### 16.1. Основной режим

Готовые политики: «Только наблюдение», «Уведомлять о проблемах», «Заменять VPS после подтверждённого IP-бана». Показывать только реализованные возможности провайдера.

Восстановление ПО без покупки добавлять после проверенного backend-действия, не создавать пустую кнопку.

### 16.2. Расширенный режим

Оставить graph-редактор. Сохранение графа не запускает его, не включает политику и не разрешает расходы автоматически.

### 16.3. Паспорт политики

Триггер, разрешённые действия, расходы, сохраняемые установочные параметры, лимиты, ресурс, последний запуск, состояние.

Остановка: «Остановятся дальнейшие шаги. Уже отправленные действия и оплата существующих VPS не отменяются автоматически».

### 16.4. Предварительный просмотр

Не только синтаксическая проверка. Пример:

```text
При новом подтверждённом IP-бане:
1. Создать один новый VPS.
2. Установить зафиксированный профиль.
3. Применить параметры логической ноды №2.
4. Дождаться проверок.
5. Переключить ресурс.
6. Удалить старый VPS.
7. Подтвердить отсутствие старого VPS.
```

Неподдерживаемый этап блокирует активацию до покупки.

## 17. State и эксплуатация

### 17.1. Ошибка загрузки

Изменить контракт loadState: существующая ошибка не теряется.

```text
Нет файла → допустимый первый запуск
Существующий файл повреждён/нечитаем → ошибка восстановления
```

При повреждении не сохранять пустое состояние поверх, не стартовать изменяющие циклы, не вызывать DNS, оставить диагностику. Первая реализация — отказ запуска с понятной ошибкой, не самовольное восстановление пустой БД.

### 17.2. Readiness

Сохранить /healthz как liveness. Добавить /readyz: state загружен, обязательная control-БД доступна, ключ шифрования доступен при требующих его функциях. Не делать readiness зависимой от текущей доступности Cloudflare/Globalping во избежание restart-loop.

### 17.3. DNS

Использовать desired_targets, applied_targets, last_error, next_attempt, last_success. Различать выбор назначения, ожидание DNS, подтверждение Cloudflare и ошибку с повтором. Не обещать распространение во всех кэшах без внешней проверки.

### 17.4. Бэкап

Отдельная согласованная процедура: operational state, control/history-БД, конфигурация, ключ шифрования. SQLite копировать с учётом WAL, не произвольным cp работающей БД. Восстановление проверить на локальной копии без реальных credentials и активных облачных воркеров.

## 18. Доступ и секреты

1. Session mutation требует CSRF.
2. Владельца определяет сервер.
3. Чужой объект — 404.
4. Не доверять клиентскому user_id.
5. Проверять принадлежность slot_id.
6. Public DTO — белый список.
7. Агент A не получает настройки B.
8. Ошибки не содержат токены/пароли/shell с секретами.
9. Шифрование — существующим механизмом.
10. Не выдавать сохранённый секрет обратно ради заполнения формы.
11. Для секрета различать «оставить», «заменить», «явно удалить», если разрешено.
12. Не менять Bearer-модель без отдельной необходимости.

## 19. Поэтапный порядок реализации

### Этап 1. Немедленные исправления безопасности

Защита state; сохранение ключа/тела платной команды; unknown-state; отсутствие нового ключа при конфликте; auto_replace=false; отдельное согласие на будущие расходы.

Файлы: registry/internal/server/run_main_impl.go; ui/pages/cabinet/main.ts и index.html; registry/internal/server/fleet_api.go; тесты рядом.

Готово: потерянный ответ не создаёт новый заказ, повреждённый state не перезаписывается.

### Этап 2. Логическая нода и нумерация

Слоты, счётчики, миграция, ownership/claim, наследование переустановкой/заменой.

Файлы: registry/internal/control/control.go; новый node_slots.go; nodes.go; manual_install.go; cloud_install.go; соответствующие server acceptance-пути.

Готово: номера стабильны, конкурентно уникальны, legacy не затронуты.

### Этап 3. Публичные подписи

Пакетные username/номер; DTO; общий frontend-helper; список/карточка/мастера.

Файлы: registry/internal/server/stats.go; control-helper идентичности; ui/pages/stats/main.ts; общий UI-helper при необходимости; stats_test.go.

Готово: пользовательские login · Нода №N, legacy — как прежде.

### Этап 4. Быстрые параметры и snapshots

Совместимая схема, типизированная валидация, ad_tag, личные defaults, immutable-specs и попытки.

Файлы: registry/internal/control/profiles.go; новые defaults/specs; registry/internal/provision/provision.go; ui/lib/vars.ts.

Готово: переопределение не меняет профиль, recovery использует тот же снимок.

### Этап 5. Все установки

Отдельное имя, vars в автопилоте, manual/cloud/Beget/graph, защищённый label, сохранение параметров замены.

Готово: значения проходят весь путь от формы до установки во всех поддерживаемых сценариях.

### Этап 6. Runtime агента

Desired/applied revisions, совместимый протокол, capabilities, транзакционное применение ad_tag, readback, rollback, отсутствие рестарт-циклов.

Файлы: registry/internal/machineapi/security.go; новый server API; control-хранилище; node/internal/agent/shared_config_sync.go; новые небольшие agent-файлы.

Готово: success после реального применения, старые версии совместимы.

### Этап 7. Recovery флотов/удалений

Startup resume, сохранённые deadlines, deleting, verifying вместо ложного admitted, отсутствие новых покупок при recovery.

Готово: рестарт на каждом этапе не создаёт дублей и недостижимых состояний.

### Этап 8. ЛК

Карточка, параметры, независимые ошибки, переходы, история флотов, ID, последствия удаления, onboarding.

Готово: создание/изменение/recovery без ручного поиска технических ID.

### Этап 9. Финансы и шаблоны

Отдельные лимиты, транзакционные резервы, паспорт, шаблоны, preview.

Готово: два процесса не обходят лимит; неподдерживаемая политика блокируется до покупки.

### Этап 10. Эксплуатация, QA, документация

Readiness, DNS, backup/restore, мобильные/клавиатурные сценарии, актуализация API и документов.

Готово: документация соответствует коду, обязательные проверки выполнены.

## 21. Команды проверки

В registry/ и отдельно в node/:

```bash
go vet ./...
go test -race ./...
go build -mod=readonly ./...
golangci-lint run ./...
```

Go форматировать gofmt.

При изменении UI:

```bash
bash scripts/build_ui.sh
bash scripts/build_ui.sh -check
```

Включить regenerated HTML в изменения.

Shell:

```bash
for script in scripts/*.sh; do
  bash -n "$script" || exit
done
shellcheck -S warning scripts/*.sh
bash scripts/check_installer_parity.sh
```

Browser-тесты: потеря ответа, повтор заказа, параметры, частичный сбой API, recovery, публичное имя. Это dev-инструмент, не runtime-зависимость сервиса.

Незапущенные проверки указывать прямо. Не объявлять verified по чтению кода.

## 23. Итоговое определение готовности

1. Имя и ad_tag задаются обычными полями при создании.
2. Не требуется редактирование текста профиля.
3. Параметры ноды не меняют общий профиль.
4. Они сохраняются при автозамене.
5. Переименование не меняет identity.
6. Применение ad_tag подтверждает агент.
7. Публичная owner-подпись — логин и постоянный номер.
8. Legacy сохраняет имя регистрации.
9. Владелец не угадывается по секрету/IP/названию.
10. Неизвестный ответ не создаёт новую покупку.
11. Процессы восстанавливаются после рестарта.
12. UI различает создание VPS, установку, регистрацию и готовность.
13. При сбое доступно безопасное следующее действие.
14. Существующие данные, агенты, секреты и квоты совместимы.
15. Тесты/сборка подтверждены командами.

**Основной принцип: сначала сохранность данных и предсказуемость действий, затем удобный ЛК поверх существующих механизмов. Не маскировать незавершённую автоматизацию новой формой или зелёным статусом.**
