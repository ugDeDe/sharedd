# Backup и restore регистратора

Скрипты:

- `scripts/backup_registry.sh` — согласованный бэкап;
- `scripts/restore_registry.sh` — восстановление с проверкой SHA256.

## Что попадает в бэкап

- `registry_state.json` — назначения, DNS-операции, события, счётчики;
- `control.db` — пользователи, владельцы нод, операции, профили;
- `registry.db` — история банов/трафика;
- `registry.toml` — конфигурация;
- `master.key` — ключ шифрования секретов Beget/установок.

SQLite копируется через `sqlite3 .backup`, а не `cp`: обычное копирование
работающей WAL-БД может дать несогласованный файл.

## Бэкап

```bash
sudo bash scripts/backup_registry.sh
# или
sudo bash scripts/backup_registry.sh --out /var/backups
```

Результат:

```text
/var/backups/sharedd-20261019T120000Z/
  registry_state.json
  control.db
  registry.db
  registry.toml
  master.key
  SHA256SUMS
```

Каталог создаётся с `umask 077`; файлы — `0600`.

## Восстановление

```bash
# 1. Сделайте бэкап текущего состояния
sudo bash scripts/backup_registry.sh

# 2. Остановите запись и восстановите
sudo bash scripts/restore_registry.sh --yes /var/backups/sharedd-20261019T120000Z
```

Скрипт:

1. проверяет `SHA256SUMS`;
2. останавливает `sharedd-registry`, если служба активна;
3. возвращает файлы с правами `0600`;
4. выставляет владельца `sharedd-registry`, если пользователь существует;
5. запускает службу.

## Важные ограничения

- Бэкап не отменяет уже созданные VPS у провайдера. После восстановления
  проверьте `cloud_resources2` и инвентарь провайдера.
- Восстановление старого `control.db` может откатить состояние операций;
  незавершённые платные заказы требуют сверки, а не автоматического повтора.
- Не запускайте восстановленную копию с реальными облачными credentials на
  машине, где уже работает другой регистратор.
- После восстановления проверьте `/healthz`, `/readyz` и журнал событий.
- Проверка восстановления на копии: используйте временный `--state-dir` и
  отключённые внешние интеграции; не выполняйте реальные покупки.
