# Приглашения и общий секрет — UI-спецификация

Статус: Phase 1, готово к согласованию контракта и реализации; `partially_verified`.
Область: существующие `/signin` и панель `#/users`, без редизайна.
Протокол, endpoints, имена полей/кодов ошибок, хранение и алгоритм миграции
определяет backend/leader. Ниже — требования к поведению, не новый API-контракт.

## 1. Основание и расхождения с текущим состоянием

Прочитаны напрямую:
- `DESIGN.md`, `docs/api-contract.md` (§2–4).
- `ui/pages/signin/{index.html,main.ts,page.css}`.
- `ui/pages/panel/views/users.ts`, `ui/pages/panel/index.html`,
  `ui/components/form.css`.
- `registry/internal/server/{cabinet_api,users_admin_api,users_control,run_main_impl,config_editor}.go`
  и `registry/internal/machineapi/security.go`.

Сейчас регистрация принимает только логин/пароль, создаёт обычного пользователя
с нулевой квотой и не выполняет автоматический вход. Приглашений в прочитанных
admin API нет. Общий Bearer используется на machine routes; персональный
authkey дополнительно проверяется при регистрации ноды. Это **не** требуемый
режим OFF на всех маршрутах. В editableConfig нет переключателя совместимости.
Текущий config-save допускает runtime apply с `persisted=false`; для этого
переключателя такой ответ нельзя представлять как успешное сохранение.

Новый запрос заменяет публичную саморегистрацию и прежнюю семантику совместимости
в затрагиваемой части. Не менять `users.enabled`, shared_proxy secrets или
panel.token под видом нового переключателя. Не использовать старый текст
«запретятся только новые регистрации» для режима OFF.

## 2. Размещение и визуальные правила

В `#/users` сохранить существующую карточку пользователей и её действия.
Добавить после неё две соседние по вертикали секции: **«Приглашения»**, затем
**«Совместимость агентов»**. Не добавлять маршрут, вкладку, метрики, поиск,
массовые операции или мастер миграции. Прямое админское создание пользователя
остаётся привилегированной операцией; оно не открывает саморегистрацию.

Повторно использовать `.card`, `.card-head`, `.card-body`, `.card-note`,
`.table-wrap .table-cards`, `.field`, `.check`, `.btn`, `.badge`, `.banner`,
существующую модалку панели и `.secret-reveal`. Новых цветов/шрифтов нет.
`--gap` 14px между секциями; `--pad` 18px внутри; заголовки 13.5px/640,
основной текст 13.5px, labels 12.5px, контролы `--ctl-h` 34px.
Важные предупреждения — `--fg`, не малоконтрастный `.dim`.
ID/URL — `--mono`; URL разрешено переносить, а не расширять контейнер.

На ≤720px таблица становится `.table-cards` с `data-label`, действия
переносятся на отдельную строку. На 320px нет горизонтального скролла страницы;
модалка ограничена viewport, её тело прокручивается, действия доступны.
Сохранить обе темы и существующую типографическую иерархию.

## 3. Админ: приглашения

### Создание

В заголовке секции одна primary-кнопка **«Создать приглашение»**.
Открывает компактную существующую модалку:
- Заголовок «Создать приглашение».
- Подпись «Одно приглашение — один аккаунт. После истечения срока ссылка не действует».
- Обязательное поле **«Срок действия»**, нативный select: только сроки,
  разрешённые согласованным backend-контрактом; начальный выбор — его default.
  Без «Бессрочно». Значения/лимиты здесь намеренно не изобретаются.
- Не добавлять email, роль, квоту, число использований или отправку письма.
- «Отмена» ghost / «Создать приглашение» primary; отправка «Создание…»,
  повторная отправка блокируется. Ошибка остаётся внутри модалки, ввод сохраняется.

После успеха в этой же модалке показать **«Приглашение создано»**, безопасный ID,
абсолютное время истечения с часовым поясом и одноразовую ссылку в выделяемом
readonly-поле. Текст: **«Ссылка показывается только сейчас. Скопируйте её и
передайте получателю. После закрытия получить её повторно нельзя»**.
Кнопки «Копировать ссылку» / «Закрыть». Копирование можно повторить, пока
модалка открыта: одноразовость означает окно раскрытия, а не одну попытку clipboard.
«Скопировано» и polite-объявление — только после успешного clipboard write.
При отказе: «Не удалось скопировать. Выделите ссылку и скопируйте вручную».
Не повторять имеющийся в rotateKey fallback, который сообщает успех без копирования.

Закрытие/Escape удаляет ссылку из DOM и памяти; список содержит только метаданные.
Секрет не попадает в local/session storage, тосты, title, журналы или аналитику.
После перезагрузки повторного раскрытия нет. Потеря ссылки: отозвать активное
приглашение и создать новое; не предлагать «восстановить ссылку».
При потере ответа создания не повторять POST автоматически: обновить список,
показать «Результат создания неизвестен. Проверьте список приглашений».

### Список и отзыв

Колонки: **Приглашение** (безопасный ID, не токен), **Создано**, **Действует до**,
**Статус**, **Действия**. Новые сверху; даты абсолютные с явным часовым поясом.
Срок и статус авторитетно задаёт сервер; локальный таймер не доказывает действительность.

| Состояние | Текст/стиль | Действие |
|---|---|---|
| Активно | «Активно», `.badge.ok` | «Отозвать», `.btn.sm.danger` |
| Использовано | «Использовано», `.badge.info` | — |
| Истекло | «Истекло», нейтральный `.badge` | — |
| Отозвано | «Отозвано», нейтральный `.badge` | — |

Подтверждение: **«Отозвать приглашение {ID}?»** / «По этой ссылке больше нельзя
будет зарегистрироваться. Уже созданный аккаунт не изменится».
«Отмена» получает начальный фокус; «Отозвать» danger → «Отзыв…».
Обновлять статус после серверного подтверждения, не удалять строку.
Если приглашение уже использовано/истекло, обновить строку и объяснить исход;
не заявлять, что созданный аккаунт отозван.

Первая загрузка — skeleton только в этой секции. Пусто: «Приглашений пока нет.
Создайте приглашение, чтобы разрешить регистрацию одного аккаунта».
Ошибка: «Не удалось загрузить приглашения» + «Повторить»; не показывать ложное
пустое состояние. Ошибка обновления сохраняет старый список с пометкой устаревания.
Нет полномочий/сервис недоступен — мутации недоступны, объяснение внутри секции.

## 4. Регистрация только по приглашению

Сохранить текущую 400px auth-оболочку, вкладки и три поля регистрации
(логин, пароль, повтор). Вкладка «Регистрация» остаётся доступной для объяснения,
но без токена показывает вместо формы: **«Регистрация только по приглашению.
Попросите администратора прислать ссылку»** и переход «Войти».
Не добавлять запрос приглашения, ручной токен-input или открытый обход.

При открытии invite URL активировать «Регистрация», показать
«Регистрация по приглашению» и обычную форму. Токен передаётся при регистрации
по согласованному контракту; не показывается как поле и не записывается в
клиентское хранилище. Формат URL/способ передачи не определяются этой спецификацией.
Если backend предоставляет проверку до отправки — «Проверка приглашения…»,
затем форма/ошибка. Если её нет, не выдумывать endpoint и не писать «проверено»:
результат подтверждается при отправке. Присутствие токена не равно его валидности.
Открытие ссылки само по себе не расходует приглашение.

| Причина, подтверждённая сервером | Текст `.banner.bad` |
|---|---|
| Истекло | «Срок приглашения истёк. Попросите администратора прислать новое» |
| Использовано | «Приглашение уже использовано. Если вы создали аккаунт, войдите. Иначе попросите новое приглашение» |
| Отозвано | «Приглашение отозвано администратором. Попросите новое приглашение» |
| Некорректно/не найдено | «Приглашение недействительно. Проверьте ссылку или попросите новое» |

Для этих конечных состояний форма недоступна, «Войти» доступно. Не отображать
личность использовавшего ссылку. Не выводить все 400/409 как ошибку пароля/логина:
сначала сопоставить согласованную причину приглашения, затем обычную валидацию.
При конфликте логина можно исправить логин и повторить с тем же приглашением;
неуспешная валидация не должна расходовать ссылку. Сервер гарантирует, что
при двух одновременных отправках создаётся не более одного аккаунта.

Сохранить `[a-z0-9_.-]{3,32}`, пароль ≥10 и сравнение повтора; ошибки связать
с полями. При отправке «Создание…», submit disabled. Сеть/503 не трактуются
как истечение или отзыв: показать возможность повторить после восстановления.
429 — «Слишком много попыток. Повторите позже» (с ожиданием, если сервер его сообщает).
Не делать автоматический retry регистрации при потере ответа: предложить вход,
если аккаунт мог уже создаться, либо явную повторную попытку.

Успех — существующий поток: очистить пароли и invite-контекст, перейти на
«Вход», заполнить только логин; «Аккаунт создан. Администратор выдаст квоту —
до этого создать ноды нельзя». Не обещать автологин или квоту от приглашения.
Активная сессия не расходует приглашение: сохранить существующий переход в кабинет.
Защита URL от referrer/логирования и очистка адресной строки согласуются с backend;
UI не передаёт invite в ссылки на статистику/кабинет или сторонним ресурсам.

## 5. Переключатель совместимости

В секции «Совместимость агентов» использовать существующий checkbox `.check`
как двухпозиционный контрол. Его видимая и доступная подпись строго:
**«Разрешить общий секрет»**. Не путать с секретами Telegram-прокси.
Рядом текстовое значение «Включено» / «Выключено»; состояние берётся с сервера,
не из localStorage и не из предположения о значении по умолчанию.

Постоянное пояснение:
> Включено: старые агенты могут обращаться к регистратору с общим токеном на
> время миграции. Выключено: персональные учётные данные обязательны на всех
> машинных маршрутах, включая регистрацию, heartbeat, отчёты, retire и получение
> конфигурации. Сам переключатель не отправляет команду остановки прокси и не
> разрывает существующие соединения намеренно. Непереведённые агенты потеряют
> доступ к API; возможны последующие изменения доступности нод по обычным правилам пула.

При наличии достоверного серверного счётчика: `.banner.warn`
**«Ноды, зависящие от общего токена: {N}. После отключения их запросы к API
будут отклоняться, пока они не перейдут на персональные учётные данные»**.
Показать время/область наблюдения, если доступны. Не выводить N из общего
количества пользователей, занятых квот или legacy-владельцев: это не доказательство
текущего способа аутентификации. При отсутствии/ошибке счётчика:
**«Число затронутых нод неизвестно. Проверьте миграцию агентов перед отключением»**.
Ноль не означает гарантированное отсутствие старых offline-агентов.

### Сохранение и подтверждение

- Загрузка состояния: skeleton/«Загрузка…», контрол заблокирован. Ошибка чтения:
  «Не удалось загрузить режим совместимости» + «Повторить»; не подставлять OFF.
- ON: явное включение пользователем отправляет сохранение, «Сохранение…»,
  контрол заблокирован. Успех только после подтверждения durable-сохранения.
- Попытка OFF сначала открывает модалку **«Отключить общий секрет?»**.
  Повторить смысл всех машинных маршрутов, отсутствие намеренного разрыва
  соединений и предупреждение со счётчиком либо неизвестностью.
  Добавить «До отключения обновите агенты и проверьте персональные учётные данные».
- Кнопки **«Отмена»** ghost (начальный фокус) / **«Отключить общий секрет»** danger.
  До явного подтверждения действующий режим остаётся ON. Escape/фон/отмена не
  отправляют изменение. Не нужны ввод фразы и дополнительный checkbox.
- После подтверждения «Сохранение…», блокировать повторную отправку. OFF отражается
  как сохранённый только после подтверждения сервера. Тост «Общий секрет отключён».
- При подтверждённом отказе сохранить прежнее серверное состояние, показать
  «Не удалось сохранить режим. Изменение не подтверждено»; разрешить повтор.
  При таймауте/неясном исходе показать «Результат сохранения неизвестен», перечитать
  состояние, не рисовать фиктивный откат и не отправлять повтор автоматически.
- Runtime-only / неподтверждённая персистентность — отдельная видимая ошибка,
  не зелёный успех: «Изменение не сохранено постоянно. Проверьте состояние регистратора».
  Такой результат блокирует приёмку. После reload и рестарта регистратора режим
  должен оставаться сохранённым. Новый контракт должен однозначно сообщать исход.
- Если актуальный режим изменился другим администратором, перечитать; любое новое
  отключение требует нового подтверждения, а не повторного применения старого намерения.

## 6. Доступность и безопасность представления

- Все действия — настоящие кнопки, поле срока с label, checkbox с связанным
  пояснением. Видимый фокус на `.box`, вся подпись кликабельна; минимум 24×24px
  область цели, включая compact-кнопки. Вкладки сохраняют arrows/roving tabindex.
- Модалки: имя, `aria-modal`, inert-фон, Tab/Shift+Tab внутри, Escape и возврат
  фокуса к инициатору. Учесть disabled-кнопки при удержании фокуса во время запроса.
- Ошибки — inline `role=alert`, успех/копирование/сохранение — polite status.
  Не озвучивать секрет целиком в live-region. Цвет всегда дополнен текстом.
- Контраст ≥4.5:1 для текста и ≥3:1 для границ/фокуса в обеих темах; проверить
  фактические пары токенов при реализации. Reduced motion без анимаций загрузки.
- URL/ID/ошибки вставлять безопасно как текст; секретная ссылка не становится
  произвольным HTML или внешним redirect. Авторизация на сервере обязательна,
  скрытая кнопка не является контролем доступа.

## 7. Передача leader/backend и проверка

До реализации согласовать в `docs/api-contract.md`: create/list/revoke и их
полномочия; допустимые сроки/default; безопасный ID, даты и окончательные статусы;
одноразовую выдачу ссылки; передачу invite и отдельные причины отказа; чтение/
сохранение режима с durable-результатом; необязательный достоверный счётчик.
Выбор URL, HTTP-методов, схемы хранения и персональной machine-аутентификации
здесь не сделан. Не строить UI на ещё не согласованных полях.

Автомиграция installer config — отдельная реализация с проверками и безопасным
откатом, не кнопка веб-панели. UI не объявляет миграцию завершённой по факту
переключения. Production deployment — только позже, после review и backups;
эта фаза не запрашивает доступ, не запускает установщики и не меняет конфиги.

Критерии приёмки следующей фазы:
1. Без invite нельзя зарегистрироваться, в том числе прямым API-запросом;
   истёкший/использованный/отозванный invite дают различимый текст; только один
   успешный аккаунт при гонке, ошибки полей не расходуют invite.
2. Создание → одноразовое раскрытие → реальное копирование или ручной fallback;
   после закрытия/refresh токена нет в списке/DOM/storage. Отзыв не удаляет аккаунт.
3. OFF требует подтверждения, действует на `POST /register`, `/heartbeat`,
   `/report`, `/retire`, `GET /config` (и любые дополнительные machine routes).
   Общего токена недостаточно; UI не обещает немедленного отключения соединений.
4. Сохранение переживает reload/restart; отказ/таймаут/persist failure не дают
   ложного успеха. Отмена OFF не мутирует режим. Проверены N>0, N=0 и неизвестный N.
5. Keyboard, mobile 320/720px, desktop, 200% zoom, обе темы; loading/empty/error/
   pending и focus-return. После реализации — UI build/check и отдельное design QA.

Проверка этой фазы: прочитаны исходники и контракт, спецификация сверена с
запросом. Приложение не изменялось; runtime, контраст в браузере, сборка и
поведение новых API не проверялись. PRODUCT.md отсутствует; существующий DESIGN.md
и узкий brief достаточны для этой добавочной спеки, инициализация/редизайн вне scope.
