## Implemented

- Full-width cabinet workspace under the existing Profiles navigation:
  `#/profiles/editor/new`, `#/profiles/editor/{id}?version={ordinal}` and
  `#/profiles/runs/{known_id}`. New graph and both template starters are visible
  in Profiles. Existing hosting views and the text-profile modal remain.
- Registry-backed palette and exact control ports; HTML blocks, decorative SVG
  wires and an equivalent visible Blocks/Connections list. Pointer node dragging,
  output-to-exec connections, canvas pan, toolbar zoom/fit, keyboard add/connect/
  remove/move, local undo/redo. Layout and viewport never enter blueprint JSON.
- Typed parameter controls, initial/observe entries, input declarations, typed
  ref/literal bindings, safe-read-only retry authoring. No opaque-handle JSON or
  credential editor. Node/input removal explicitly clears affected refs/entries.
- Persistent selectable diagnostics, UTF-8 request/graph limits, saved numeric
  version versus version-PK distinction, explicit version CAS, read-back before
  accepting save, preserved conflicts and ambiguous-write reconciliation.
  Save never creates a run. Native dirty-leave Save/Discard/Stay and unload guard.
- Exact bundled Nodehost/Beget JSON fixtures; templates only replace local drafts.
  Beget/IP runtime gates are persistent and prevent both run and policy enable.
- Separate run review with unchecked consent, owned connection selector, balance
  freshness/scope, manual Nodehost configuration (RAM/disk in GB, no hostname),
  numeric text-version read/PK verification, non-secret vars and registry port.
  Optional named deployment identity is retained in the request intent.
- Run detail by known ID with 5-second visible-only, single-flight GET polling,
  terminal/leave cleanup, checkpoint journal, allowlisted handle output, numeric
  pinned-version resolver, revisioned cancel/resume and conservative read retries.
  Unknown outcomes never become a new-key automatic mutation retry. Ambiguous
  create keeps the original body/key in memory for an explicit identical replay;
  ambiguous cancel/resume locks command controls for this session, retaining GET.
- Node management now offers a resolved saved graph/version-PK and the same typed
  input form. Manual mode has no automatic-purchase claim; Profile mode explicitly
  grants the version's actions. New current-ban consent is unchecked; persisted
  true is displayed without pretending it is a new default. Returning from a
  saved Manual policy does not reuse the old true checkbox. Policy input DOM is
  preserved across background statistics refreshes.
- Scoped token-based CSS, dark/light support, mobile panel tabs (Blocks first),
  native dialogs, labelled controls, persistent error descriptions, focus
  preservation on keyboard movement, reduced-motion handling and wrapped IDs.

| `POST /api/me/profile-runs/{id}/resume` | `{expected_revision,checkpoint_id,decision}` and key; decisions `reconcile`, `retry_safe`, `acknowledge`; `202` acknowledgement, not completion. The checkpoint control carries its displayed revision. |
| `GET /api/me/nodes/{id}/management` | `200 {mode,profile_version_id,inputs,process_current_ban,revision,current_resource_id}`; no active_run_id assertion. |

## Deliberate gates and remaining gaps

- Published latest-version/format discovery is not available. Numeric opening and
  copying are supported, but unresolved published profiles and unverified default
  sentinels are excluded from legacy profile-ID-only text installers. A user can
  explicitly read a published numeric text version, save a local text copy and
  use it; the graph run form can directly pin that numeric text version's PK.
  Existing text HTTP payloads remain unchanged. No guessed latest or destructive
  graph copy endpoint is used.
- Execution forms support the verified `connection_id`, `configuration_ref` and
  `installation_profile_version_id` declarations plus non-secret primitives.
  Executable create/install bindings must use these checked inputs, rather than
  numeric literals masquerading as text-version PKs or arbitrary handles. Other
  structurally valid graphs remain authorable/saveable but can be execution-gated.
- No provider catalog presets, quote, run-list, operation-detail, publish,
  credentials/secret-handle picker, resource-linking or layout endpoint was added.
  A missing current policy resource blocks Profile enable rather than fabricating
  a link. Beget remains design-only, regardless of successful validation.
- No guarantee of an exclusive multi-writer lock: backend authoring CAS is not an
  atomic compare-and-append transaction. Read-back content is compared before a
  saved baseline is accepted. Unknown writes keep the sent snapshot separate from
  later edits, and never silently advance the expected version.
- Drafts and uncertain intents are memory-only. Native unload warns before losing
  an uncertain create intent; no graph/vars/credentials are persisted in browser
  storage. Acknowledged run URLs are the durable access path.
- The runtime still owns actual purchase/SSH/readiness semantics. UI validation
  does not claim spending permission, exact retry scheduling, independent health
  postconditions, automatic policy creation, progress percentage, cost or refund.

## Follow-up: PROFILE-enable UX — one switch, no dead-end banner (2026-10-19)

User complaint: after a node is installed from a cloud resource, enabling
automation was blocked with «Текущий ресурс не связан. Включение Profile
заблокировано.» Even though the node's cloud resource is already discoverable by
`node_id` from `GET /api/me/cloud-resources`. With the backend companion
(PUT management auto-links `current_resource` from the node's bound ready cloud
resource; frozen contract unchanged), the front-end blocker is wrong.

### UX section — management panel behavior now

1. **Hard blocker removed.** `blueprint-management.ts` derives smart defaults
   from the caller-passed resource (found by `node_id` in the already-loaded
   resources list — no extra fetch). `connection_id` is prefilled into the
   instance form from `resource.connection_id`; saved policy inputs (when the
   loaded graph version matches the policy's saved `profile_version_id`) keep
   priority over the prefill. The CloudResource DTO carries no configuration
   snapshot or install-profile PK, so `configuration_ref` stays an
   empty-but-editable structured form and `installation_profile_version_id` is
   picked by the user through the existing text-version picker.
2. **Compact checklist instead of a wall.** When a graph version is loaded and
   no gate reason applies, the gate banner shows one line, e.g.
   «Чек-лист · Подключение: из ресурса #12 ✓ · Конфигурация: заполните параметры
   VPS в форме · Профиль установки: выберите текстовую версию». The checklist
   flips to ✓ live (config once any field is typed, install profile once the
   text version is loaded — exposed via the new `InstanceForm.installedTextVersion()`).
   Only genuinely missing required things disable the save button, each with an
   inline hint in the same line: no bound resource at all, beget provider gate,
   graph version not loaded, runtime gate, text version not picked, consent
   unchecked.
3. **One switch semantics.** Radio Profile → prefilled form → one primary button
   labelled «Включить автоматизацию» (manual mode keeps «Сохранить ручной
   режим») with the existing consent copy (paid replacement disclosure;
   process-current-ban defaults off).
4. **Dead case stays neutral.** If the node has no bound resource at all, the
   gate shows one short hint linking to `#/resources` («хостинг-ресурсов») — no
   blocker wall; the facts row likewise links to the bound-by-node resource with
   «свяжется автоматически» instead of a bare «не связан».

PUT body is unchanged: `{mode:'profile', profile_version_id, inputs,
process_current_ban, expected_revision}`; the backend companion performs the
auto-link, so the UI no longer requires `current_resource_id != null`.
