# sharedd — СРМД + клиенты по общему секрету

## Что нового

### 1. Активные клиенты считаются только по общему секрету

Нода суммирует per-user серии `telemt_user_unique_ips_current{user="..."}`
теперь **только по пользователям, которых раздаёт регистратор**
(`shared_proxy.users`, приходят в `GET /config`). Локальные юзеры ноды
(чужие записи `[access.users]`, которые агент никогда не перезаписывает)
в число активных клиентов больше не входят — ни в KPI «Активные клиенты»,
ни в колонке «Клиенты», ни в таблице СРМД.

Пока shared-конфиг ещё не приехал с регистратора (первые секунды после
старта агента), действует прежнее поведение — сумма всех серий, чтобы не
рисовать «нет данных» до первого sync.

- `node/healthcheck.go` — `buildMetricsSnapshot(samples, sharedUsers)`,
 `promUserLabel`, фильтр по общему секрету (агрегаты unique IPs и
 подключений + per-user серии в снапшоте).

### 2. СРМД — Система Распределения и Масштабирования Доменов

Новая вкладка панели **«СРМД»** (между «Мастера и DNS» и «Журнал»):
таблица **домен | активные пользователи** и настройки системы.

Логика (реализация — `registry/srmd.go`):

- регистратор считает текущих активных клиентов по общему секрету на
 мастерах доменов и хранит последние значения по каждому домену — даже
 если живого мастера на домене сейчас нет (балансировка опирается на эти
 числа; в панели «последние известные» помечены звёздочкой);
- **рост пула**: здоровых нод больше, чем `домены × max_nodes_per_domain` —
 при включённом «Разрешить СРМД создавать новые домены» (по стандарту
 **выключено**) СРМД создаёт сиротские домены с инкрементом от основного:
 `shared.ddproxy.xyz` → `shared1.ddproxy.xyz`, `shared2.…` — сама
 дописывает их в `cloudflare.domains` (персистится в `registry.toml`) и
 раздаёт им мастеров обычной селекцией. Сначала разворачиваются ранее
 свёрнутые («свободные») домены, и только потом создаются новые;
- **сжатие пула**: нод стало меньше — лишние СОЗДАННЫЕ домены сворачиваются
 в **CNAME** на оставшиеся, балансируя пользователей: крупные уходят
 наименее загруженным на данный момент. Основной и добавленные вручную
 домены не сворачиваются никогда; цепочек CNAME не бывает (цели — только
 из выживших). Пример: было 4 домена (1500/380/1000/1400 клиентов), нод
 стало мало и нужно 2 домена → `shared2` → CNAME `shared`, `shared3` →
 CNAME `shared1`, итог 2500/1780;
- **выключено**: создание отключено, а нод слишком много в очереди —
 алерт вверху экрана панели;
- анти-флап: действие только после ~минуты устойчивого условия
 (20 тиков селекции); CNAME-записи пишутся с ретраем не чаще раза в минуту;
- события журнала: `srmd_domain_created` / `srmd_domain_folded` /
 `srmd_domain_unfolded`.

Новая секция конфига (hot-apply из панели, персистится):

```toml
[srmd]
enabled = false # разрешить СРМД создавать новые домены
base_domain = "" # пусто = первый из cloudflare.domains
max_nodes_per_domain = 5 # максимум нод на домен
```

Ручной DNS-push («Перезаписать DNS сейчас») корректно перезаписывает и
свёрнутые домены — CNAME'ом на цель.

## Совместимость

- старые агенты (без фильтра по общему секрету) продолжают работать:
 регистратор просто получает прежнюю сумму клиентов;
- при отсутствии `[srmd]` в конфиге поведение прежнее (выключено, лимит 5);
- state-файл читается старый (блок `srmd` появляется сам), конфиг без
 `[srmd]` валиден.

## Дополнительно

### Статистика банов: один IP = один бан

Исправлено задвоение банов в статистике (панель и публичный `/dashboard`):
повторные баны одного и того же адреса (перепроверки, ре-баны под новым
node_id после нового мастерства) больше не добавляют новых строк — адрес
учитывается ровно один раз. Если адрес со временем восстанавливается
(GP re-verify прошёл, `ban_lifted`), запись о его бане **убирается из
статистики** — и только после этого его новый бан снова считается первым.
Смена IP оператором восстановлением не считается: брошенный заблокированный
адрес остаётся в статистике, пока сам не пройдёт перепроверку.

- `registry/db.go` — дедупликация `recordBan` по IP, `liftBanIP`;
- `registry/healthcheck.go` — удаление строки при `ban_lifted`;
- `registry/panel.go` — агрегаты журнала пересчитаны по той же семантике
  (бан открывается по `globalping_blocked` на адрес, закрывается уходом ноды,
  убирается восстановлением адреса).

### Фильтры журнала

Вкладка «Журнал» панели, помимо групп (Все / Мастер·DNS / Блокировки / Ноды /
Система), получила:

- **тег-фильтр** — выпадающий список конкретных типов событий
  (`master_elected`, `dns_updated`, `srmd_domain_folded`, …);
- **поиск по ключевым словам** — все слова через пробел ищутся в типе/теге
  события, node_id, IP, домене и детали (регистр не важен);
- счётчик «найдено N из M»; окно выборки расширено до 1000 событий.


## СРМД: ручное управление доменами, баннер и прокси-ссылки

### Баннер без ложных тревог по CNAME-доменам

Домен, свёрнутый СРМД в CNAME, больше не попадает в предупреждение
«Домены без мастера … A-записи для них не выставлены»: своей A-записи у
него нет по определению, клиенты ходят через CNAME.

### Ручной ⇄ СРМД: перевод доменов под контроль и обратно

В таблице вкладки «СРМД» появилась колонка «Управление»:

- **«под СРМД»** — ручной домен насильно переводится под контроль системы и
  с этого момента может сворачиваться в CNAME при сжатии пула
  (`POST /panel/api/srmd-domain {"domain":…, "action":"take"}`);
- **«в ручной»** — домен СРМД возвращается в ручной режим и больше не
  сворачивается; если он свёрнут прямо сейчас — разворачивается
  (отложенная CNAME-запись отменяется, мастер назначается на ближайшей
  селекции) (`"action":"release"`).

События журнала: `srmd_domain_taken`, `srmd_domain_released`.

### Публичный API `/proxylinks`

`GET /proxylinks` — JSON с актуальными `tg://proxy`-ссылками по каждому
managed-домену, у которого есть свой мастер:

	tg://proxy?server=<домен>&port=<порт мастера>&secret=ee<секрет 32 hex><SNI в hex-ASCII>

Свёрнутые СРМД в CNAME домены и домены без мастера в список не попадают —
возвращаются, когда мастер будет назначен. Эндпойнт открыт без токена
(ссылки предназначены для раздачи пользователям), монтируется вместе с
публичными страницами и выключается `[panel] enabled = false`.
